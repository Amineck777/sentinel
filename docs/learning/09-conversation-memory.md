# 09 会話の記憶:エヴァがマスターのことを覚えている仕組み

設計は ADR 0116。このノートは「なぜこの形にしたか」を後から読み返すためのもの。
実装は4つの PR に分けて進め、入った分から「実装メモ」の節に書き足していく。

---

## 記憶の3つの層

**一言で:** 原文は全部残し、そのうち最近の分はそのまま、古い分は要約と事実にして渡す。

**背景:** LLM は、プロンプトに入れたことしか知らない。エヴァの文脈は8192トークンなので、全部の会話は入らない。
かといって要約だけにすると、要約の誤りを直せなくなる(ユウカは原文を消していたので、これが起きた)。

**しくみ:**

```
話す ─→ messages(原文。消さない保管庫)
          │
          ├─ 直近の会話 ───────────→ 短期記憶:そのままプロンプトへ(約2500トークン)
          │
          └─ 会話の区切りで LLM が読む ─→ 長期記憶
                                          ├ episodes:いつ・何があったか(キャラ別)
                                          └ facts:マスターについての事実(全キャラ共有)
                                                 │
次に話すとき ←──── 固定枠＋検索で選んだ分だけ ←────┘
```

| 層 | 人間でいうと | 中身 | 作り直せるか |
|---|---|---|---|
| 原文 | 日記帳そのもの | すべての発言 | ─(これが元) |
| 短期記憶 | 今している話 | 直近の会話をそのまま | 毎回原文から取る |
| 長期記憶 | 覚えていること | 出来事の要約、事実 | 原文から何度でも |

**学び:** 「一次記録(原文)」と「二次記録(要約・事実)」を分けると、二次記録の作り方をあとで変えても困らない(ADR 0105)。

---

## なぜ「会話の区切り」で記憶を作るのか

**一言で:** GPU は1つの仕事しか同時にできないので、マスターが話していないときに作る。

**背景:** 記憶づくり(要約と事実の取り出し)も gemma4:e4b に頼む。毎ターン直後に動かすと、続けて話しかけたときに返事が遅れる。
夜だけにすると、昼の話を夕方に思い出せない。

**しくみ:**
- 最後の発言から約15分たったら、まだ記憶にしていない発言をまとめて LLM に渡す
- アプリ終了時にも試す。強制終了で間に合わなかった分は、次の起動時に作る(`memory_jobs` に「どこまで作ったか」を残す)
- 作っている途中でマスターが話し始めたら、会話を優先して記憶づくりは後回し
- 区切り前の話は短期記憶に入っているので、困らない

---

## 事実に付ける印

LLM が取り出す事実は、ときどき間違える(冗談を本気にする、推測を事実と思い込む)。だから印を付ける。

| 印 | 例 | なぜ |
|---|---|---|
| 分類 | 好み、予定・約束、仕事、人間関係、プロフィール | 画面で絞り込む、予定は期限で片付ける |
| 事実か推測か | 「コーヒーが苦手」(本人が言った)/「疲れているらしい」(推測) | 推測を断定して話さないため |
| 確信度・重要度 | 0〜1 | 思い出す順番、固定枠に入れるか |
| 出典 | 元の発言の ID | 間違っていたら原文を見て直せる |
| 状態 | 有効 / 置き換え済み / 忘れた | 訂正しても古い方を残し、考えが変わった経緯も記録になる |

## 思い出し方:固定枠＋2種類の検索

**一言で:** 大事なことは毎回、残りは「言葉が同じもの」と「意味が近いもの」の両方で探す。

**背景:**
- キーワード検索(SQLite の FTS5、trigram)は軽くて、固有名詞や日付に強い。ただ trigram は3文字ずつ区切るので「仕事」のような2文字の言葉や、「コーヒー」と「珈琲」の言い換えに弱い
- 意味の検索(ベクトル検索、sqlite-vec)は文を数字の並び(埋め込み)にして近さを比べる。言い換えに強いが、日付や名前の完全一致は苦手

**しくみ:**
1. 固定枠:固定指定した事実と、重要度の高い事実を約300トークン分、毎回入れる
2. マスターの最新の発言で、FTS5 とベクトル検索をそれぞれ引く
3. 2つの順位を RRF(Reciprocal Rank Fusion:各リストでの順位の逆数を足す)で1つにまとめ、重要度と新しさで並べ直す
4. 出来事は「今のキャラと話したもの」だけ、事実は全キャラ分から選ぶ
5. 約700トークン分をプロンプトへ

**学び:** RRF は「点数の単位が違う2つの検索」をまとめる簡単な方法。点数ではなく順位だけを使うので、調整がいらない。

## 人格と記憶をコアで組み立てる

**一言で:** 人格の文を1つのファイルに置き、コアが「人格＋記憶」を system として送る。Modelfile はそのファイルから作る。

**背景:** Ollama は、リクエストに system があると Modelfile の SYSTEM を捨てる(ノート05)。
記憶を user 発言に混ぜると、モデルが記憶を「マスターの発言」と取り違えやすい。

**しくみ(予定):**
- system の中身:人格の文 →「マスターについて覚えていること」→「以前の出来事(3日前など、相対的な日付つき)」→ 記憶の使い方の注意(「記録によると」と言わない、推測は断定しない)
- 人格ファイルの指紋(ハッシュ)を `turn_logs` に残すので、人格の文をいつ変えたかもあとで分かる

---

## 忘れる、を二段階にする

| 操作 | 原文 | 出来事・事実・検索用データ | 使い道 |
|---|---|---|---|
| 「忘れて」(会話・画面) | 残す | 思い出さない印を付ける | ふだんの訂正 |
| 「完全に削除」(画面のみ、確認あり) | 消す | 消す | 本当に消したいもの |

完全削除では「ここで削除があった」という印だけを中身なしで残す。
**注意:** それより前に取ったバックアップには残る。

## 実装の順番(予定。1つずつ PR にする)

1. DB 版4、セッションの継続(6時間)、短期記憶をトークン数で切る、人格ファイルの組み立て、`turn_logs`
2. 記憶づくり(区切りの検出、JSON で取り出し、`episodes`・`facts`・FTS5)
3. 埋め込みモデルと sqlite-vec、ハイブリッド検索、プロンプトへの挿入、評価セットに記憶の問題を追加
4. 設定画面(歯車→記憶)、会話での訂正、忘れる・完全に削除

## 実装メモ PR1:記憶の土台

### 短期記憶をトークン数で切る

**一言で:** 「直近40発言」をやめ、「新しい発言から順に、約2500トークンに収まるまで」にした。

**しくみ:**
- トークン数は `core/sentinel_core/memory/budget.py` で**多めに**見積もる(日本語1文字=1トークン、英数字4文字=1トークン、1発言ごとに+4)。少なめに見積もると文脈(num_ctx)からあふれ、Ollama が古い側を黙って切り捨てる。多めなら、あふれない
- `Store.recent_history`(`core/sentinel_core/memory/store.py`)が、新しい順に足していき、上限を超える手前で止める。最新の1発言だけは、長すぎても必ず入れる(入れないと今の話が届かない)
- 本当のトークン数は、Ollama が返す usage を観測ログに残す。見積もりとの差を見れば、上限を詰められるか分かる

### 再起動しても会話を続ける

**一言で:** 画面が session_id を持っていなくても、同じキャラと6時間以内に話していれば、そのセッションの続きにする。

**しくみ:** `ChatService._resolve_session`(`core/sentinel_core/agent/service.py`)
1. 画面が渡したセッションが今のキャラのものなら、それを使う
2. 違えば `Store.resumable_session` で「今のキャラの最新セッション」を引き、`memory.session_resume_hours` 以内なら使う
3. どちらでもなければ新しいセッション

別キャラのセッションは続けない(論点5:出来事はキャラ別)。そのため、発言ごとに `messages.character_id` を残すようにした(DB 版4。既存の発言はセッションのキャラで埋める)。

**ハマりどころ:** SQL で汎用モード(キャラ ID が NULL)を探すとき、`character_id = ?` に None を渡しても一致しない(NULL = NULL は「不明」になる)。`character_id IS ?` を使う。

**今の制限:** 画面のチャット欄には、再起動前の発言は表示されない(エヴァは覚えているが、画面は空から始まる)。表示は PR4 の設定画面と一緒に考える。

### 人格の文を1ファイルにする(file モード)

**一言で:** `character.yaml` に `llm.system_prompt: file` と書くと、`persona/system.md` を人格の文としてコアが送る。

**しくみ:**
- 読み込みは `core/sentinel_core/character/pack.py` の `_read_system_file`。ファイルが無い・空・Pack の外(`../` など)を指すときは、Pack を無効にして理由を残す
- 送る文を決めるのは `core/sentinel_core/agent/prompts.py` の `build_system`。file モードは人格の文だけを送り、SENTINEL の土台プロンプト(「あなたはSENTINEL」)は足さない。人格とぶつかるため
- PR3 で、この後ろに記憶を足す
- `ollama run eva` 用の Modelfile は `scripts/build_modelfile.py` で同じファイルから作る。人格の文の正が1か所になる(ADR 0106)

### 自己観測ログ(turn_logs)

返答ごとに1行。失敗したターンも `error` つきで残す。

| 列 | 中身 |
|---|---|
| model / character_id | どのモデル・キャラで答えたか |
| persona_hash | 送った system の SHA-256 の先頭12桁。人格の文を変えると変わる |
| prompt_version | 組み立て方の版(`prompts.PROMPT_VERSION`)。組み立てを変えたら上げる |
| recalled_ids | 思い出した記憶の ID(PR3 から入る。今は空) |
| first_token_ms / total_ms | 最初の文字が出るまで / 全体の時間 |
| prompt_tokens_est / prompt_tokens / completion_tokens | こちらの見積もり / Ollama が返した実数 |

ログを書く処理が失敗しても会話は止めない(`contextlib.suppress`)。ログは「無くても会話は続く」もの。

### やってみる

```powershell
# 直近の観測ログを見る(DB の場所はノート03)
python -c "import sqlite3,os;p=os.path.expandvars(r'%LOCALAPPDATA%\sentinel\sentinel\data\sentinel.db');[print(r) for r in sqlite3.connect(p).execute('SELECT started_at,model,persona_hash,first_token_ms,total_ms,prompt_tokens_est,prompt_tokens,error FROM turn_logs ORDER BY rowid DESC LIMIT 5')]"
```

## 実装メモ PR2:記憶づくりとキーワード検索

### 全体の流れ

```
返答が終わる ─→ scheduler.on_turn_finished(15分のタイマーを張り直す)
マスターが話す ─→ scheduler.on_user_activity(タイマーと記憶づくりを止める)
15分たつ ─────→ run_pending
                 └ セッションごとに「まだ記憶にしていない発言」を取り出す(longterm.pending_messages)
                    └ 約2500トークンずつに区切る
                       └ 記憶係として LLM を呼ぶ(extractor.extract)→ JSON
                          └ 出来事・事実・訂正・記録を1トランザクションで保存(longterm.save_extraction)
```

ファイル:`core/sentinel_core/memory/scheduler.py`(いつ)、`extractor.py`(LLM に何を頼み、どう読むか)、`longterm.py`(保存と検索)。表は `store.py` の版5。

### 「どこまで記憶にしたか」の目印

**一言で:** `memory_jobs` に、処理した発言の rowid の範囲を残す。`done` と `skipped` の最大の `to_rowid` が目印(watermark)。

- 失敗(`failed`)は目印にしない。次の機会にやり直す
- 同じ範囲で3回失敗したら `skipped` を書いて先へ進む。壊れた出力が続くと、毎回 GPU を使い続けるため
- 挨拶だけ(マスターの発言が無い)のまとまりは、LLM を呼ばずに `skipped`

### 止めても半端な記憶が残らない理由

記憶係の返事を待っている間にマスターが話しかけると、`asyncio` のタスクごと取り消す(`Task.cancel()`)。
保存は LLM の返事が全部そろってから1回のトランザクションで行うので、取り消された回は何も書かれない。目印も進まないので、次の区切りでやり直される。

**学び:** 「途中で止められる処理」は、副作用(DB への書き込み)を最後の1か所に集めておくと安全になる。

### LLM の出力を寛容に読む

小さなモデルの JSON は崩れることがある。`extractor.parse` は次のように受け止める。

| 崩れ方 | 扱い |
|---|---|
| 前置きや ``` の囲み | 最初の `{` から最後の `}` までを読む |
| 0〜1 の外の数、文字の数 | 0〜1 に丸める。読めなければ既定値 |
| 知らない分類 | `other` |
| 日付でない期限(「来週」) | 捨てる |
| 範囲外の発言番号 | 捨てる。出典が空ならマスターの発言を出典にする |
| 知らない事実の番号への訂正 | 捨てる |
| JSON がまったく無い | 失敗として記録し、やり直す |

事実の ID(32桁)は LLM に見せず、`F1` `F2` の短い番号に置き換えて渡す。書き写し間違いを防ぐため。

OpenAI 互換の `response_format: {"type": "json_object"}` で「JSON だけ返す」ように頼む(`OpenAICompatClient.complete_json`)。受け付けないサーバーなら外してやり直す。

### キーワード検索(FTS5 の trigram)

**一言で:** 3文字ずつずらした窓を OR で探し、一致が多いものほど上に来る(bm25)。

- `query_terms("仕事の話。コーヒーは?")` → 3文字の窓「仕事の」「事の話」「コーヒ」「ーヒー」…と、2文字の語「仕事」
- trigram は3文字未満を探せないので、2文字の漢字語・カタカナ語は `LIKE '%仕事%'` で別に探す
- 長音「ー」は語の中に出る(コーヒー)ので、区切り文字にしない
- 見つかったもののうち、事実は全キャラ分、出来事は今のキャラの分だけを返す(論点5)。忘れたもの・置き換え済みのものは返さない

**ハマりどころ:** FTS5 の検索式で `"` を含む語は `""` と2つ重ねて囲む。そのまま入れると構文エラーになる。

### 起動時と終了時

- 起動して30秒後に、前回の積み残しを処理する。ただし起動時にエヴァが挨拶すると、そこで一度止まり、挨拶のあとの15分の区切りで処理される(会話を優先するため)
- 開発中に窓1で Ctrl+C したときは、最大20秒だけ残りの記憶づくりを待つ。配布版はアプリがコアを止める(kill)ので待たない。間に合わなかった分は次の起動で作る
- 初めて PR2 の版で起動すると、これまでの会話すべてが「まだ記憶にしていない」扱いになる。何回かに分けて記憶づくりが走る
